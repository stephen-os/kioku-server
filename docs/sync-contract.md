# Sync Contract

How Kioku clients and the server stay in agreement. This is the contract every
client implements and the server enforces. It is settled before the schema,
because every table depends on it.

> **Status:** all decisions below are settled.

## Decisions (settled)

| Decision | Choice |
| --- | --- |
| Entity identity | UUID v4, generated by the client |
| Conflict granularity | Entity level, not field level |
| Conflict rule | Last write wins on `updated_at` |
| Delete vs. edit | **Edit wins.** A concurrent edit resurrects a deleted entity |
| Ordering | Integer `position`, resolved by the same LWW rule |
| LWW clock | Client `updated_at`, server rejects >5 min in the future |
| Tombstone retention | 90 days, then hard delete |

Rationale for edit-beating-delete: the user can always delete again, but cannot
un-lose content. This is the opposite of what most sync systems do, and it is
the right call for personal data.

## Model changes from the desktop

The desktop's domain model carries over. Its *storage* model does not. Three
simplifications cut the syncable surface roughly in half, and each one removes
a class of conflict rather than solving it.

**Choices are inline on Question.** A choice is never independently meaningful
and is always edited alongside its question. Inlining removes an entity and
makes question edits atomic.

**Tag membership is an array on the entity, not a join table.** The desktop has
`card_tags`, `quiz_tags` and `question_tags`. Syncing join rows means syncing
relationships, which conflict in ways entities do not. Instead a Card or
Question carries `tag_ids: uuid[]`, and retagging is an ordinary edit under
LWW. `Tag` remains an entity because it has a name worth editing.

A tag is scoped to exactly one container, a deck or a quiz, enforced by a check
constraint. Cards draw from their deck's tags and questions from their quiz's,
which is what the desktop's separate `tags` and `quiz_tags` tables meant. One
entity with two scopes rather than two entities keeps the sync surface smaller.

**Favorites are a boolean column.** The desktop used join tables because a
local install had several local profiles sharing one deck table. Server-side,
a deck belongs to exactly one user, so `is_favorite` is just a column.

### Syncable content

Five entities, bidirectional, LWW:

`Deck` · `Card` · `Tag` · `Quiz` · `Question`

### Progress

`StudySession` · `QuizAttempt` (with question results inline)

These are records of things that happened, and two devices essentially never
produce conflicting versions of the same one. They still carry the ordinary
sync columns and resolve by the same last-write-wins rule rather than a
separate union merge, for two reasons: it keeps one code path instead of two,
and a session legitimately changes once, when it goes from started to
completed. Treating that as an append-only insert would drop the completion.

### Not synced

`User` is server-authoritative. Account data has one source of truth and no
offline edit path.

## Sync metadata

Every syncable entity carries these. No exceptions, including append-only ones.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Client-generated. Stable across devices |
| `user_id` | `uuid` | Owner. Every query scopes by this |
| `created_at` | `timestamptz` | Client clock, informational |
| `updated_at` | `timestamptz` | Client clock. **The LWW key** |
| `deleted_at` | `timestamptz` null | Tombstone. Null means alive |
| `server_seq` | `bigint` | Server-assigned, monotonic per user. The pull cursor |

## Protocol

Two endpoints.

### Pull

```
GET /sync?since={server_seq}
```

Returns every entity owned by the caller with `server_seq > since`, including
tombstones, plus the new high-water mark. An empty `since` means a full sync.

```json
{
  "seq": 4812,
  "decks":     [ ... ],
  "cards":     [ ... ],
  "tags":      [ ... ],
  "quizzes":   [ ... ],
  "questions": [ ... ]
}
```

### Push

```
POST /sync
```

Client sends locally-changed entities. The server applies the conflict rule,
assigns `server_seq`, and returns what it accepted along with any entity where
the server's copy won, so the client can reconcile.

Push is **idempotent**: re-sending an entity whose `updated_at` matches the
stored copy is a no-op. This is what makes retry-after-timeout safe, and it is
why ids are client-generated.

## Conflict resolution

On receiving an entity, the server compares against its stored copy:

1. No stored copy → accept, assign `server_seq`.
2. `incoming.updated_at > stored.updated_at` → accept.
3. `incoming.updated_at < stored.updated_at` → reject, return the stored copy.
4. Equal timestamps → tie-break on `id` lexicographically, so every node
   reaches the same answer without coordination.

Writes within a push follow dependency order (decks and quizzes, then tags,
then cards and questions), not the order the payload declares them. A batch
that creates a quiz and its tags together would otherwise violate a foreign
key.

Deletes are ordinary updates that set `deleted_at`. So the edit-beats-delete
rule needs no special case: an edit with a later `updated_at` than the delete
simply wins, and clears `deleted_at`.

## Sequence assignment

`server_seq` is a monotonic per-user counter, and it has a subtle failure mode
worth getting right the first time.

**The gap problem.** If transaction A takes seq 5 and transaction B takes seq
6, and B commits first, a client pulling at that instant receives 6 and
advances its cursor past 5. When A commits, that change is never delivered.
The client is now permanently missing data with no error.

**The fix:** never hand out a high-water mark past an in-flight transaction.
Either assign `server_seq` at commit time under a per-user row lock, or track
the mark separately and only advance it past fully-committed sequences.

This is the single easiest thing to get wrong here, and the failure is silent.

## Clock skew

`updated_at` comes from the client, so a device with a wrong clock can win or
lose every conflict.

Using server time instead would fix that but break offline ordering: a week of
offline edits would all arrive stamped with the same instant, losing the order
they happened in.

**Settled:** client `updated_at` stays the LWW key. The server rejects
timestamps more than 5 minutes in the future and returns a clock-skew error the
client surfaces, so a badly-set clock fails loudly instead of silently winning
every conflict.

## Tombstone retention

Tombstones must outlive the longest plausible offline period, or a device that
was away too long will resurrect deleted content on its next sync.

**Settled:** retain 90 days, then hard delete. A client whose `since` cursor
predates the purge horizon is told to discard its local state and do a full
sync.

## Consequences

- Every write path maintains the sync columns. No back doors.
- Deletes are soft. Hard deletes happen only via the purge job.
- The sync payload must tolerate unknown fields, so a client that has been
  offline across a schema change degrades rather than breaks.
- The API is versioned from the first release for the same reason.
